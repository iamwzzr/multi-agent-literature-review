## 优先级 1：影响用户找到和核对正确原文

### A. 中文问法与跨行断词会漏检（已复现）

生产 SearchIndex 的合成对照：同一段英文中，multi- 换行 lingual 对 multilingual 查询返回 0 条，拼合后返回 1 条；中文“需不需要查资料”对 conditionally acquires documents 返回 0 条，英文原词查询返回 1 条。

实际两篇 PDF 共发现 92 处英文字母连字符跨行模式。这个数量不是“92 次检索失败”，而是说明该解析现象确实存在；漏检由上述控制样例验证。

固定 G04 比较问题在当前两篇可用资料上的首轮前 6 段，未命中 RAG 第 3 页和 Self-RAG 第 4 页两个标准目标；固定英文检索式命中 2/2。G01、G02 首轮则命中目标页。G04 还涉及本地缺失的 FLARE，因此不能把这次小库探针当作完整三论文评测，更不能从首轮未命中断言多步 Agent 最终一定失败。

建议：在不改变原始证据的前提下，建立可回映的断词检索视图；加入子问题分解、跨语言查询扩展，之后对比 embedding/融合排序/重排。先固定 Recall@k 和论文/页码标准，避免只凭长报告判断效果。

### B. 新的精确定位尚未接到前端（代码核查确认）

后端有 evidenceId、字符锚点和定位接口，但 src/Evidence.tsx 仍以 #page= 页码打开 iframe PDF；没有读取定位接口、文字层高亮或 bbox。用户现在仍需要在整页找句子。

建议：先在证据面板展示短引文、前后文与匹配/歧义状态，再评估带文字层的 PDF 查看器与坐标解析。提取文本字符位置不等于 PDF 版面坐标。OCR、表格与双栏阅读顺序不属于本轮已解决能力。

### C. 本地资料与大库环境未准备完整（实测配置/文件）

- 其余 5 篇固定资料内容未在当前 data/papers 下找到。
- data/papers-100 按清单文件名检查为 0/100。清单和工具已下载，不等于 PDF 已下载。
- 本机生效配置 MAX_PAPERS=40、MAX_TOTAL_PAGES=1500，不能直接覆盖队友的完整 100 篇库评测需求。

建议：先统一固定 7 篇的路径、版本和哈希，再准备 100 篇；区分全库索引上限与单轮精读预算。不要仅提高资料数量而不验证检索覆盖、运行时间和调用成本。

## 优先级 2：可理解的异常、引用完整性与资料管理

### D. 空白 PDF 上传显示成功，生成才发现无证据（HTTP 已复现）

用临时创建的合法单页空白 PDF 上传，返回 HTTP 200 和 file_id；仅使用该上传 ID 生成后，返回 taskStatus=blocked、verification=no_evidence，unresolved=[]。系统没有编造报告，但用户缺少“无可提取文本”的具体原因。

建议：上传阶段检查可提取文本，返回可读性状态或明确错误；生成阻塞时保留具体原因。扫描件 OCR 可作为后续可选增强，不能将第一版未承诺的 OCR 当成回归失败。

### E. 比较表同名字段覆盖导致参考文献漏列（纯函数已复现）

构造 cells.dataset='Result [[1]]'、conditions.dataset='Matched settings'、正文无引用的报告。生产 citationParts 识别出单元格中的 1 条引用，但 reportReferences 返回 0 条参考文献。

原因：src/ReportPreview.tsx 的 reportReferences 用 {...row.cells,...row.conditions} 合并，条件字段覆盖同名单元格。只在引用仅存在于表格等边界下漏列；不能据此宣称所有现有报告都有引用缺失。当前后端通常也把比较行写入正文，因此有时会掩盖此问题。

建议：分别遍历 cells 与 conditions 的值，然后对引用编号去重；增加同名字段与表格独有引用回归测试。

### F. 审核详情读取失败没有显式提示（状态探针 + 代码核查）

生产 reportWarning 在 taskStatus=completed、verification=passed、audit 缺失时仍返回正常交付提示。streamBackendReview 在流结束后的运行详情请求失败时 catch 到 null，AuditSummary 又在无 audit 时不显示。

这不等于后端没有审核，stream 的 passed 可能是真实结果；问题是版本、比较表、审核详情和用量可能缺失，用户却不知道详情加载失败。

建议：将“生成结果已收到”与“审核详情已加载”分开；显示详情读取失败、可重试，不把缺失详情说成无问题。此次没有模拟完整浏览器网络中断链路。

### G. 重复上传与删除管理不完整（HTTP + 源码核查）

相同 PDF 两次上传均返回 200，得到不同 file_id。底层按哈希复用文件，不代表磁盘重复保存；但前端按 ID 汇总，且最多 20 条，没有逐项移除入口。API 也没有完整上传列表/删除管理。

建议：按项目+内容哈希复用上传记录或提示重复；先提供从本轮选择中移除，再明确区分删除引用、删除上传记录和删除原始材料。

### H. 前端测试稳定性需要改进（本轮实际超时）

构建成功，SSR 契约探针超时，两者并不矛盾。建议将纯协议逻辑测试从 Vite/React 加载中拆出，单独测试请求构造、引用汇总和状态恢复；UI/SSR 另跑，并保存阶段耗时。不要将本轮超时写成业务断言通过。

## 建议实施顺序

1. 先准备固定资料与版本路径，建立可信、可复现的验收基线。
2. 优化断词与中文问法检索；每次用相同问题比较目标页命中。
3. 前后端对接定位状态、短引文和原文上下文，再做 PDF 高亮。

5. 完善上传去重/移除和前端测试稳定性。
6. 最后运行固定真实模型样例，统计审核完成率、质量、耗时与调用成本，再扩大到完整资料库。
